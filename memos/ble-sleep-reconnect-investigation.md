## 登場するパラメータの解説

### 2つの独立した管理レイヤー

BLE には **2種類の接続**があり、それぞれ**別のコードが別のパラメータで**管理している。

```
┌─────────────────────────────────────────────────────────────┐
│  レイヤー A: board.c の独自管理（このキーボード専用）         │
│                                                             │
│  管理する接続: セントラル（右）↔ ペリフェラル（左）          │
│                                                             │
│  制御するパラメータ:                                        │
│    SLEEP1/2/3_TIMEOUT_MS  → 何秒後に省電力モードへ移行するか │
│    接続インターバル         → BLE 無線の起動頻度              │
│    接続レイテンシ           → ペリフェラルが応答をサボれる回数 │
│    SUPERVISION_TIMEOUT    → 切断を検知するタイマー           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  レイヤー B: ZMK 本体の管理（全 ZMK キーボード共通）          │
│                                                             │
│  管理する接続: セントラル（右）↔ PC（ホスト）                 │
│                                                             │
│  制御するパラメータ:                                        │
│    CONFIG_ZMK_IDLE_TIMEOUT         → ACTIVE → IDLE          │
│    CONFIG_ZMK_IDLE_SLEEP_TIMEOUT   → IDLE → ディープスリープ │
└─────────────────────────────────────────────────────────────┘
```

---

### BLE 接続の3つの基本パラメータ

#### 1. 接続インターバル (Connection Interval)

BLE 無線チップが「次の通信を待ち受けるために起動する」間隔。

```
短い ─→ 無線が頻繁に起動 ─→ 応答性が高い・電池消費大
長い ─→ 無線がたまにしか起動しない ─→ 省電力・応答が遅くなる

単位: 1.25ms
ZMK デフォルト: 6 単位 = 7.5ms（約133回/秒）
board.c SLEEP3: 48 単位 = 60ms（約16回/秒）
```

#### 2. 接続レイテンシ (Connection Latency)

ペリフェラル（左側）が「返事をサボれる」回数の最大値。

```
レイテンシ = 0 → 毎回の接続イベントで応答必須
レイテンシ = 4 → 4回スキップして5回目に応答 OK

「ペリフェラルの実質的な最大応答間隔」は以下で計算できる:
  インターバル × (1 + レイテンシ)

ZMK デフォルト: 4
  → 実質応答間隔: 7.5ms × (1+4) = 37.5ms

board.c SLEEP3: (4+7)/8 = 1（整数除算）
  → 実質応答間隔: 60ms × (1+1) = 120ms
```

#### 3. スーパービジョンタイムアウト (Supervision Timeout)

「この時間内に一度も通信がなければ切断とみなす」タイマー。

```
単位: 10ms
ZMK デフォルト: 400 単位 = 4,000ms = 4秒
※ board.c はこの値を変更していない（常に4秒）

BLE 仕様の必須制約:
  SUPERVISION_TIMEOUT > 2 × (1 + Latency) × Interval × 1.25ms

board.c SLEEP3 での検証:
  4,000ms > 2 × (1+1) × 48 × 1.25ms
  4,000ms > 240ms  ← 規格上はOK、しかし実機で問題が発生
```

---

### ZMK のアクティビティ状態（レイヤー B）

ZMK が管理するキーボード全体の状態遷移。

```
キー入力 / トラックボール操作
         │
         ▼
   [ ACTIVE 状態 ]  ← 通常動作
         │
         │ CONFIG_ZMK_IDLE_TIMEOUT 経過後
         │ 設定値: 未設定 = ZMK デフォルト 30秒
         ▼
   [ IDLE 状態 ]
   ・PC との BLE 接続パラメータを省電力に変更
   ・スプリット接続は board.c が別途管理（この状態変化とは独立）
         │
         │ CONFIG_ZMK_IDLE_SLEEP_TIMEOUT 経過後
         │ 設定値: 9,000,000ms = 150分（2時間30分）
         ▼
   [ SLEEP 状態 = ディープスリープ ]  ← ★ここが問題
   ・BLE 無線を完全停止
   ・キーを押すまで完全無反応
   ・復帰後は PC ↔ セントラル・セントラル ↔ ペリフェラル
     の両接続を最初から再確立する必要がある
```

| パラメータ | このキーボードの設定値 | ZMK デフォルト値 |
| --------- | ------------------- | ---------------- |
| `CONFIG_ZMK_IDLE_TIMEOUT` | **未設定（30秒）** | 30,000ms (30秒) |
| `CONFIG_ZMK_IDLE_SLEEP_TIMEOUT` | **9,000,000ms (150分)** | 900,000ms (15分) |

---

### board.c の段階的スリープ（レイヤー A）

セントラルが「スプリット接続のインターバル」を段階的に伸ばす独自実装。

| 段階 | 発動（最後の操作から） | インターバル | 実質最大応答間隔 | 4秒タイムアウトまでの余裕 |
| ---- | --------------------- | ------------ | ---------------- | -------------------------- |
| ACTIVE | 〜5秒 | 7.5ms | 37.5ms | **107倍** |
| SLEEP1 | 5秒〜 | 15ms | 45ms | **89倍** |
| SLEEP2 | 20秒〜 | 30ms | 60ms | **67倍** |
| SLEEP3 | 50秒〜 | 60ms | 120ms | **33倍** |

> 計算上はいずれも切断されないはず。  
> ただし 30分の離席で問題が起きないことから、SLEEP3 での切断は発生していない可能性が高い。

### タイムライン全体図

```
t = 0          キー入力 / トラックボール操作

               │
t = 20秒       │ [board.c] SLEEP2 → スプリット接続インターバル 30ms
               │
t = 30秒       │ [ZMK] IDLE → PC との接続パラメータが省電力に
               │
t = 50秒       │ [board.c] SLEEP3 → スプリット接続インターバル 60ms
               │
               │                           ← この範囲で 30分〜？時間が経過 →

               │
t = 150分      │ [ZMK] SLEEP（ディープスリープ）
               │   ・右（セントラル）のBLE完全停止
```

### ケース1: 〜30分放置（問題なし）

board.c は SLEEP3 に入っているが、スーパービジョンタイムアウトは 4 秒であり、  
60ms インターバルでは十分な頻度で接続イベントが発生するため切断は起きていない。

---

### ケース2: 一晩（7〜8時間）放置（確実に再現）

```
t = 150分    [ZMK] ディープスリープ開始
              ・右（セントラル）: BLE 無線停止
              ・左（ペリフェラル）: BLE 無線停止
              ← 5〜6 時間、両方ともBLE停止状態 →
              ← PC も Windows スリープ中 →

翌朝、PCスリープを解除（マウス or 電源ボタン等）:

    0秒        PC の Windows が起動
               Windows の BT スタックが初期化
                 ↓
    数秒後     右（セントラル）をキー押下で起動
               セントラルがアドバタイズ（接続待受け）開始
                 ↓
    5〜15秒後  Windows がセントラルを発見して再接続
               → 右のキーが使えるようになる ✓
                 ↓ ← この後、セントラルがペリフェラルを探し始める
    5〜15秒後  ペリフェラル（左）がセントラルを発見して再接続
               → 左のキーが使えるようになる ✓（右より大幅に遅れる）
```

**全体の接続シーケンス:**

```
PCスリープ解除
     │
     ├──── 数秒 ────→ Windows BT 起動
     │                   │
     │                   ├─ 5〜15秒 ──→ 右（セントラル）とPC再接続
     │                   │                  │
     │                   │                  ├─ さらに5〜15秒 ──→ 左（ペリフェラル）とスプリット再接続
     │                   │                  │                        │
     ↓                   ↓                  ↓                        ↓
    0秒               数秒後           右が使える               左が使える
                                      (5〜20秒後)             (10〜30秒後)
```

→ **「右はすぐ使えるのに左だけ10秒ほど遅い」症状と完全一致**

### 発生しきい値の推定

| 放置時間 | ZMK 状態 | board.c 状態 | 症状の主因 | 実際の発生 |
| -------- | -------- | ------------ | ---------- | ---------- |
| 〜30分 | IDLE | SLEEP3 | なし | **発生しない（確認済み）** |
| 30分〜150分 | IDLE | SLEEP3 | board.c? | **不明** |
| **150分〜** | **ディープスリープ** | **無関係** | **ZMK再接続遅延** | **発生する（推定）** |
| 7〜8時間 | ディープスリープ | 無関係 | ZMK + PC 再接続 | **確実に発生（確認済み）** |

> 30分では発生しないことから、board.c SLEEP3 が原因である可能性は低い。  
> 主因は ZMK ディープスリープ（150分で発動）と考えられる。

> → チップの差異ではなく、`board.c` の有無がこのキーボードと他のキーボードの違いと考えられる。

## 原因の考察

### 最有力仮説: ZMK ディープスリープ後の再接続遅延

- 確実に再現するのは一晩放置（7〜8時間）
- 150分でZMKディープスリープが発動するため、翌朝は必ずこの状態
- ディープスリープからの再接続は「直列2段階」で起きるため、左（ペリフェラル）が右より遅くなる
- 30分の離席で問題が起きないことと矛盾しない

### board.c が原因の可能性

- 30分の離席（SLEEP3状態）で問題が起きないため、低い
- ただし、中間的な時間帯（30分〜150分）での発生有無が未確認
- もし30分〜150分でも発生するなら board.c が関与している可能性を再検討する必要がある

## 対策案と試行順序

### 問題の性質の整理

```
【主要問題（確実）】ZMK ディープスリープ（150分後）からの再接続遅延
【不確定問題】board.c SLEEP3 での接続不安定（30〜150分の放置で発生するか不明）
```

---

### 対策 C: ZMK ディープスリープを遅らせる ← 最初に試すべき対策

`CONFIG_ZMK_IDLE_SLEEP_TIMEOUT` を大幅に延ばし、一晩放置ではディープスリープに入らないようにする。

**変更ファイル:** `boards/shields/torabo_tsuki_lp/torabo_tsuki_lp_left.conf` と `torabo_tsuki_lp_right.conf`

```diff
- CONFIG_ZMK_IDLE_SLEEP_TIMEOUT=9000000   # 現在: 150分
+ CONFIG_ZMK_IDLE_SLEEP_TIMEOUT=43200000  # 変更後: 12時間（12×60×60×1000）
```

- **期待効果**: 翌朝ケースでディープスリープに入らず、スプリット接続が維持されたまま朝を迎えられる
- **リスク**: 電池消費がやや増えるが、SLEEP3状態での待機なので影響は軽微
- **確認方法**: 一晩放置して翌朝キーを押す

---

### 対策 B: board.c の SLEEP3 を廃止 ← 対策 C で解消しない場合

30〜150分の時間帯でも問題が発生していることが判明したら試す。

**変更ファイル:** `src/board.c`

```diff
- #define SLEEP1_TIMEOUT_MS 5000
- #define SLEEP2_TIMEOUT_MS 15000
- #define SLEEP3_TIMEOUT_MS 30000
+ #define SLEEP1_TIMEOUT_MS 30000   // 30秒
+ #define SLEEP2_TIMEOUT_MS 60000   // 1分
  // SLEEP3 は廃止（最大 SLEEP2 の 4× インターバル止まり）
```

---

### 対策 A: board.c 自体を廃止 ← より根本的な対策

スプリット接続の動的パラメータ変更を完全になくし、他のキーボードと同じ動作にする。

- `src/board.c` を無効化（または削除）
- 省電力効果は失われるが、接続安定性が最大になる

---

### 推奨する試行順序

```
Step 1 ── 対策 C を試す
           （CONFIG_ZMK_IDLE_SLEEP_TIMEOUT を 12時間に延長）
              │
              ├─ 翌朝テストで問題解消 ──→ ★ 完了
              │
              └─ 翌朝テストでも問題発生
                  または
                  30分〜150分でも発生することが判明
                       │
Step 2 ─────────────────→ 対策 B or A を追加で試す
```

### BLE パラメータの制約式

```
BLE 仕様 (Bluetooth Core Spec):
  supervision_timeout_ms > 2 × (1 + latency) × interval_ms

本機 SLEEP3 の値で検証:
  interval    = 48 単位 × 1.25ms = 60ms
  latency     = 1
  timeout     = 400 単位 × 10ms = 4,000ms

  4,000ms > 2 × (1 + 1) × 60ms = 240ms  ✓ 規格上は OK

  ※ 実機では問題が発生しているため、規格外の要因（チップ固有の挙動等）の可能性あり
```
